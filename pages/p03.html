The AXI shelf: gh-axi, chrome-devtools-axi, quota-axi and friends

The tools Kun built to the AXI spec: what each one wraps, what the agent gains, how you install them, and who else adopted the pattern.
SourceAXI catalog, kunchenguid/axi ↗
TL;DR — Most of Kun's AXIs do not reimplement anything. They sit in front of a tool that already works (the gh CLI, the chrome-devtools MCP server, each vendor's own quota endpoint) and change only what the agent sees: compact output, a dashboard when called with no arguments, a hint about what to run next, and errors it can act on. quota-axi is the strictest of them: it reports quota and refuses to decide anything. tasks-axi is a newer sibling that edits a markdown backlog and is not in the official catalog. Each one installs as a skill, as a session hook, or with nothing at all.

The previous page laid out the ten AXI principles. A spec is only an argument until something is built to it, and Kun's answer was to build the same idea several times over, each time on a different kind of backend.

The wrapper pattern

An AXI (Agent eXperience Interface) is a command-line tool shaped for an agent that drives a shell. The reference implementations are mostly thin layers. The agent runs a short command; the AXI calls the real tool underneath; the AXI then reshapes the answer before the agent reads it. That reshaping is where the value sits. Output comes back as TOON (Token-Oriented Object Notation, a compact text format for tables and objects that the spec credits with about 40% savings over the same data as JSON). Lists say how many items exist and what was cut. Empty results say "0 open" outright rather than printing nothing. Every response ends with a short help block naming the likely next command.

gh-axi: GitHub, through the CLI you already trust

gh-axi wraps GitHub's official gh CLI. It covers issues, pull requests, workflow runs, releases, Projects boards, gists, secrets and stacked PRs, and you still need gh installed and logged in. Run it with no arguments and it prints a dashboard of the current repo's open issues and PRs. If a read fails, it says unknown (fetch failed) instead of printing a zero, because to an agent a silent empty list looks like a fact. A --fields flag returns only the columns you ask for. Failures come back once, as a structured error, so a long stream of gh diagnostics doesn't fill the context.

The README backs this with a benchmark: 17 GitHub tasks, five repeats each, claude-sonnet-4-6 as the agent and an LLM judge. In his runs gh-axi completed every task, against 86% for raw gh. Those numbers are Kun's own and self-reported. The previous page covers what they do and don't show. The limits are practical ones. It needs Node 20+, and a few features need recent gh versions, for example --attach needs gh 2.99.0 or later.

chrome-devtools-axi: a browser that stays open

chrome-devtools-axi wraps chrome-devtools-mcp, an MCP server that drives Chrome (MCP, the Model Context Protocol, is the standard way to plug tool servers into an agent). A CLI process exits after each command, but a browser must survive between them. So the first command starts a small bridge process on localhost port 9224. The bridge holds one long-lived MCP session, and each later command talks to it. The bridge checks its own health and restarts itself if Chrome has died.

What the agent sees is a short accessibility snapshot of the page, in which the clickable elements carry refs such as @g1:1, followed by a hint like "Run click @g1:1 to click the link". The g1 part is a generation number. If the page has changed since the snapshot, the action fails with STALE_REF instead of clicking the wrong thing. In his 14-task browser benchmark (same model, same five repeats), Kun reports 57% fewer input tokens than calling the raw MCP server it wraps. The skill also tells agents to skip Chrome for pages a plain fetch can read.

A sibling, agent-browser-axi, applies the same design to Vercel's agent-browser. It installs from npm or source, does not appear in the catalog, and its repo was last pushed on 2026-07-31.

quota-axi: how much is left, and nothing else

Agents need quota state before they choose where work can safely run.
quota-axi README

quota-axi answers one question: how much subscription capacity remains, per provider and per window, and when it resets. Each vendor exposes this differently, through different auth stores, window names and endpoints. quota-axi gives each provider an adapter and maps the results into one schema. Each row carries the percent remaining, a projected runway, a confidence level, the window that is the binding limit, and the reset time. Its README lists about nineteen providers, including Claude, Codex, Cursor, Copilot and Grok. The catalog row names five.

It is defined as much by what it refuses to do. It never picks a provider for you:

It never routes, ranks a winner, or orders providers preferentially.
quota-axi README, Safety guarantees

Nor does it proxy traffic, log in, import browser cookies, or mint or rotate a credential. When a token has expired, it asks the vendor's own CLI to refresh it. It also makes no claim that 40% left on one vendor is worth the same as 40% on another. One provider failing while the rest answer still exits 0, and the report shows the failure, so a periodic check keeps working. The caveats: it needs Node 22.19 or newer, and on macOS it won't read Keychain-held tokens until you run it once with --allow-keychain-prompt and approve the request. Until you do, some providers can show as stale or unavailable.

In use: In Larry's setup, quota-axi feeds a periodic usage check so the assistant can see how much subscription capacity is left before it starts big work.

tasks-axi: a backlog the model doesn't rewrite

tasks-axi differs from the rest because it doesn't wrap another tool. It edits a hand-editable backlog.md in place. Its README names the problem plainly:

Every backlog mutation today regenerates markdown through the model, which is expensive output tokens and risks dropped, duplicated, or reordered items.
tasks-axi README, Why

Changing one task's status becomes a short command and a one-line confirmation. The file round-trips byte for byte, so a human can still edit it, and a lockfile plus atomic writes stop a hand edit and a CLI edit from overwriting each other. It borrows dependency edges and a "ready" query from beads. The storage sits behind a small Store interface, so other backends can be added later. Only markdown has shipped so far. SQLite and GitHub, Jira or Linear backends are listed as planned. It is not in the official catalog. One community entry, frontier-axi, already turns its output into tasks-axi tickets.

Installing: skill, hook, or nothing

Every tool on the shelf offers the same three install paths. An Agent Skill is a small folder in a shared format that the agent loads when a task matches its description. In these repos the skill is a stub that points the agent at the live CLI rather than copying its docs, so the instructions don't go stale:

npx skills add kunchenguid/gh-axi --skill gh-axi -g      # skill, all projects
npm install -g gh-axi && gh-axi setup hooks               # ambient session hook
# or just tell the agent: Execute `npx -y gh-axi` to get GitHub tools.

The second path is the "setup hooks" pattern, which corresponds to the spec's principle 7, ambient context. A SessionStart hook is a command that the agent's harness runs when a conversation opens, with its output fed in as context. gh-axi setup hooks registers one for Claude Code, Codex and OpenCode, so every session starts with the repo's open issues and PRs already visible. You opt in explicitly, the setup is safe to run twice, and it repairs a stale path. The spec warns that this context loads on every session, so it must be tiny. gh-axi, chrome-devtools-axi and tasks-axi all ship setup hooks; the quota-axi README documents only the skill and the CLI. The emphasis differs, too. The AXI spec calls the hook the primary integration and the skill a secondary one, while each tool's own README recommends the skill first. Use either, or both.

The catalog grew without him

The official table lists four tools: gh-axi, chrome-devtools-axi, quota-axi and lavish-axi. Lavish gets its own page next. As of 2026-11-21 the community table has 118 entries, generated from a catalog.yaml that contributors add to. They follow the same move Kun made: take a CLI or an MCP server that already works and put the AXI shape on top. glab-axi does to GitLab's CLI what gh-axi does to GitHub's. otter-axi turns Otter.ai's hosted MCP server into a headless CLI, as chrome-devtools-axi does for Chrome. sqlite-axi runs capped, read-only queries. axi-axi scaffolds new AXIs and runs compliance checks against a candidate CLI.
