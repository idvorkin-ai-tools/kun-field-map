How Kun builds

The habits that repeat across the repos, and the task pipeline he hands to his own agents.
Sourcekunchenguid/kun · ENTRY.md ↗
TL;DR — Read enough of Kun's repos and the same moves keep turning up. Each README opens by naming a problem. The output is shaped for an agent to read. A skill ships next to the binary. Tools run on your machine and reuse logins you already have. Claims come with a benchmark, and the tools call each other. His own instruction file turns this into a task pipeline: research, plan in a visual artifact, build the simplest thing, then validate adversarially. His videos add the human side. He spends his attention at the start and end of a task and lets agents fill the middle.

This is a reading of the repos, not a manifesto Kun wrote. Each pattern was checked against at least two repos; exceptions are named.

The README is the argument

Most of the tool READMEs follow one shape. There is a centred title, a row of badges, and then one h3 line that states the whole idea. Treehouse's is “Manage worktrees without managing worktrees.” (A worktree is a second checkout of the same git repo, so two agents can edit in parallel.) Next comes a short paragraph about the reader's pain, and only then the tool. justroll shows it most plainly:

You want to record a talking-head video over a couple of screens.justroll README

The next sentence is the “but”: OBS scenes, a forgotten second display, an evening spent lining up audio. rough-cut-axi and trial-by-combat open with “You want” too. autopreso uses the past tense (“You wanted to give the talk, not build the deck.”). Treehouse and headless ask a question instead. The shape is common but not universal: gnhf, gh-axi and the dotfiles README have no h3 tagline. The discipline: name the problem in one sentence before shipping the tool.

Built for the agent as the user

The AXI spec (page 2) sets the habit. Output is in TOON, a compact, indented text format. The spec claims about 40% fewer tokens than JSON, a figure Kun reports himself. Every response ends with a help[] block that suggests the next command. chrome-devtools-axi prints Run `chrome-devtools-axi click @g1:1` ... after opening a page, and quota-axi and tasks-axi end their sample output the same way.

The second half of the pattern is distribution. Each AXI ships an Agent Skill, a small instruction file the agent loads only when the task calls for it, installed with one line:

npx skills add kunchenguid/gh-axi --skill gh-axi -g

The same line appears for lavish-axi, quota-axi, chrome-devtools-axi and tasks-axi. gh-axi's skill is a “discovery stub” that defers to the live CLI help, so an installed copy can't go stale. Some repos skip the binary entirely: vision and headless are skills and nothing else.

Local-first, and no new keys

The tools run where your data already lives, and they reuse logins you already have. lavish-axi calls itself local-first, and its hosted sharing is opt-in. backpass reads agent transcripts straight off disk (or over SSH to your own machines). Its README says it has no API keys of its own, so every model call goes through a harness you have already logged into. quota-axi reads the local auth files of the agents you run and calls only first-party endpoints. It reads the macOS Keychain only after you grant permission. headless goes furthest. It sets up a remote machine with the admin password left in your secret store, and the agent only ever names the entry. The position: a new tool should not become a new place where your credentials sit.

Benchmarks as arguments

When Kun claims a design is better, he usually builds a harness to test it. All of the figures below are his own, self-reported runs.

  • axi publishes two tables, both run on Claude Sonnet 4.6. The browser benchmark has 490 runs (14 tasks × 7 conditions × 5 repeats), and chrome-devtools-axi scores 100% at the lowest average cost. The GitHub benchmark has 425 runs, with gh-axi at 100% against 86–87% for the gh CLI and GitHub MCP (Model Context Protocol, the standard tool-server interface).
  • superpowers-bench asks whether an agent picks the right skill without being told. It runs 20 tasks, with and without a hint, across Claude Code, Codex and OpenCode, and grades skill selection by precision and recall. The README describes the design. This page does not repeat its scores.
  • org-bench (written up on Substack; the repo has no README) wires six well-known org-chart memes as multi-agent teams. Every agent and the judge run on gpt-5.4, and each team builds the same spreadsheet app. The judge's scores ranged from 3.00 to 3.62. The more useful finding is about how each topology failed. In the fully connected team, every peer tested the formula bar and nobody checked the arithmetic.

The habit cuts both ways: in his June video he warns against installing popular skills that publish no evaluation.

Plumbing, dogfooding, names

Release hygiene. Most of the npm tools carry a CI badge and a release-please badge. release-please is a GitHub Action that turns conventional commit messages into version bumps and changelogs. Among the READMEs pulled for this map, it shows up on gnhf, lavish-axi, backpass, justroll, gh-axi, chrome-devtools-axi, tasks-axi, autopreso and m87. no-mistakes and runner-up use their own release workflow instead.

Dogfooding. The tools are built from each other. vision's review board runs on lavish-axi, launched through npx -y lavish-axi. backpass's default review UI needs lavish-axi on your PATH. firstmate gives each task a treehouse worktree and ships projects through no-mistakes. In the high-throughput video, firstmate calls quota-axi before it dispatches an agent, so work goes to whichever subscription has the most quota left. The kun repo's own ENTRY.md routes validation through no-mistakes and planning through Lavish.

Names. gnhf is “good night, have fun”, what he tells his agents before bed. no-mistakes makes sense once you type it: git push no-mistakes. justroll's tagline opens with “We're rolling.” In the June video he says Lavish was nearly called the filthy rich editor.

PR policy. The tools take contributions; gnhf has a CONTRIBUTING.md, for example. The personal repos do not. The kun README says the repo is his own knowledge base, so it does not accept PRs. The dotfiles README is blunter:

Feature requests and pull requests are not accepted here, and PRs are auto-closed.dotfiles README

The working method

ENTRY.md is the instruction text Kun gives an agent that is acting on his behalf. For feature work it sets a fixed order: research, planning, implementation, validation. A bug fix replaces planning with reproduction. A refactor replaces it with guardrails, meaning tests added before anything moves. Planning means a Lavish HTML artifact with SVG diagrams and open questions, revised until the user approves. Implementation gets one line:

Find the simplest solution that satisifies the requirements. Avoid adding anything that's not strictly required.kun / ENTRY.md

(The typo is in the original.) Validation is adversarial: use the no-mistakes gate if the repo has a remote, and a fresh subagent review if it doesn't.

Four videos fill in the human side. In the June workflow walkthrough he works almost entirely in the terminal, to keep his hands on the keyboard and to have the same setup on every device. He talks to agents by voice, keeps his global memory file short, and moves conditional knowledge into skills. The central move is how he treats a finished task. He doesn't read every diff. He acts like an engineering director: he sets up the process, sends the change through no-mistakes, and decides how closely to review from the risk assessment and the evidence attached to the PR. His time goes to the start (planning in Lavish) and the end (holding the quality bar). The middle belongs to agents, and the longer the middle runs, the more tasks run in parallel. gnhf stretches it overnight, treehouse keeps parallel sessions apart, and firstmate takes over the juggling of tabs.

The July dev-environment video starts from reproducibility. A fresh Mac gets its whole setup from Nix and nix-darwin, so a machine an agent has broken can be rebuilt in one step. The September high-throughput video runs everything through a single firstmate conversation. A dispatch rules file, which firstmate writes from his stated preferences, picks the harness and model for each kind of task. He hides the tool-call stream: attention, not tokens, is the bottleneck. The November work-from-anywhere video adds machines. A headless Mac mini on Tailscale hosts remote “secondmates” that keep working while the laptop is closed, and he can reach the same sessions from his phone over SSH.

The same idea runs through all of it. Every tool removes one reason for the human to sit in the loop, and the human's own work is to plan well and judge the result.
