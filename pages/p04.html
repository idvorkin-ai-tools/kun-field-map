Lavish: HTML is the new markdown

Why Kun wants agents to answer in web pages, and the review loop that lets you mark up a page instead of typing corrections into chat.
Sourcekunchenguid/lavish-axi on GitHub ↗
TL;DR — Coding agents can already write a good HTML page: a plan with diagrams, a comparison table, a clickable prototype. The weak part is what happens next, when you have to describe your changes back in chat. Lavish opens the agent's HTML file in a local browser, lets you click any element or select any text and attach a note, and hands those notes to the agent, which waits on a long poll and then rewrites the file. It is a CLI built on Kun's AXI rules, it runs locally, and setup is one skill install.

Markdown became the default format for agent output because it renders in a terminal and a chat window. It also caps what an answer can be: headings, bullets, a code block, maybe a table. A plan that needs a system diagram, three design options side by side, or a prototype you can click has nowhere to go. Kun's view is that agents are already fluent in HTML, so the format should be HTML, and the missing piece is a way to review it.

HTML is the new markdown. Lavish is the new editor for your HTML artifacts.lavish-axi README

Why HTML needs its own review tool

Asking an agent for an HTML artifact is easy. Giving feedback on one is where it breaks down. You open the file, find the box that is wrong, take a screenshot or write "the third card in the second row, the one about caching", and paste that into chat. The agent has to work out which element you meant, and you have turned an interactive page back into a static picture plus a paragraph of prose. The README puts the cost in one line:

That loses the thing HTML is best at: interactivity.lavish-axi README

Lavish fixes the feedback step, not the writing step. The agent still writes an ordinary HTML file on disk. Lavish serves it in a browser tab with a small review layer around it, so the place where you notice a problem and the place where you comment on it are the same place.

The review loop

The loop has four steps. The agent writes an HTML file. It runs lavish-axi <file>, which starts (or reuses) one background server and opens a browser tab. The artifact runs inside a sandboxed iframe, and Lavish injects a small script for annotations and layout checks, but no styles of its own, so the saved file looks the same whether you open it through Lavish or straight from disk.

You click an element or select a passage, type a note, and queue it. Notes collect until you press Send. Meanwhile the agent has run lavish-axi poll <file>, a long poll: one command that blocks until there is something to return, instead of the agent re-checking every few seconds and paying tokens for each empty check. When you send, the poll returns your notes with what each was attached to. The agent edits the file, Lavish live-reloads the tab while keeping your scroll position and any half-typed note, and the agent posts a short reply into the page's conversation panel. When you are done, End session tells the agent to stop polling, and a plain reopen afterwards is refused unless you ask for more review.

What you can point at

  • Elements and text. A note carries the element's CSS locator, or the selected text with range anchors. Inside a table it also names the visible row and column, so sorting the table does not make a note look misdirected.
  • Mermaid whiteboards. Mermaid is a text syntax for flowcharts and sequence diagrams. If you ask for an editable whiteboard, the agent writes the diagram in Mermaid and Lavish turns it into an Excalidraw canvas you can drag and redraw. Your edits go back as a summary plus a scene file; the agent then updates the Mermaid source, which stays the source of truth. Otherwise the default figure is hand-drawn inline SVG.
  • Images. Paste or drop a reference screenshot onto a note. The agent receives a local file path, not raw bytes.
  • Layout problems. After the page settles, Lavish checks for clipped text and controls pushed off screen, and lists them in an inbox. Detection never wakes the agent; only you choosing to queue a fix does.
  • Answers. A decision page can have real radio buttons and inputs, and their values come back as structured answers rather than prose.

Playbooks: teaching the agent to draw

A review tool does not help much if the first draft is a wall of text. Lavish ships guidance for the writing side. lavish-axi design prints design direction, and lavish-axi playbook <id> prints focused advice for a kind of artifact: diagram, table, comparison, plan, code, input, explanation, slides. The agent is told to open every playbook that matches before writing, since one plan often includes a comparison and a diagram. An optional revisions legend lets the agent tag which blocks changed in each round, so a one-sentence fix on a long page is easy to find.

AXI, applied

Lavish is an AXI, Kun's name for a CLI designed for agents (see the ten principles). Three of those principles carry most of the weight here. Output is TOON, a compact text format that Kun's spec says saves about 40% of tokens against equivalent JSON. The poll is a long poll, so waiting for a human costs one command, not a stream of retries. And contextual disclosure means each response suggests the likely next commands, so the agent learns the tool by using it rather than by reading a manual first.

The same idea shapes how it is installed. The skill is a short stub that points the agent at --help, design and playbook, so an old installed copy cannot drift from a newer CLI. Lavish declares no MCP server (MCP, the Model Context Protocol, is the usual way to hand an agent a tool); the CLI is the whole interface.

Local-first, and where that stops

The core loop needs no cloud: the file, the server and the session state live on your machine, under ~/.lavish-axi/. A few things to know before relying on it:

  • Sharing is a third party. lavish-axi share uploads the page to ht-ml.app, which is not part of Lavish. Shares are public by default; --private adds a generated password. The host has no delete, so unpublishing swaps in a locked placeholder.
  • Phone review trusts your network. With Tailscale running, the server also listens on the tailnet address so you can review from a phone. The README warns that this exposes an unauthenticated server that can read local files to anything on that network, so the tailnet must be trusted.
  • Telemetry is on by default in the npm release: command name, version and platform, no arguments or content. LAVISH_AXI_TELEMETRY=0 turns it off.
  • Tab-local drafts. Notes you have queued but not sent live in that browser tab only; closing it can lose them.

How Kun routes work through it

Kun's public kun repo includes an ENTRY.md that tells an agent how to work "like Kun". Its planning and explainer steps both start by reading the Lavish skill and building an interactive artifact: findings, proposals and open questions for a plan; the most direct path to understanding for an explainer. Feedback in Lavish is answered by revising the artifact until the plan is approved. One line in it sums up the style:

Aggressively avoid long text prose and prefer big picture SVG diagrams to explain concepts.kunchenguid/kun, ENTRY.md

He uses it outside planning too. In his essay on treating AGENTS.md like a neural net, proposed rule edits are shown in Lavish with their diffs and evidence, and he accepts or rejects each one. In a workflow video he calls it central to how he plans complex work, then runs the same feature request with and without it to show the difference.

Installing it

npx skills add kunchenguid/lavish-axi --skill lavish   # add -g for all projects
# then, in Claude Code:
/lavish let's discuss our plan here

No npm install is needed; the skill runs the CLI through npx -y lavish-axi. Two alternatives: tell any agent to use npx -y lavish-axi with nothing installed, or install globally and run lavish-axi setup hooks, which adds a session-start hook for Claude Code, Codex, OpenCode and GitHub Copilot CLI so a fresh session can resume an in-flight review. The npm package is the source of releases.

In use: Used daily in Larry's setup: plans, comparisons and reviews become Lavish pages that get annotated in the browser instead of answered in long chat replies.
